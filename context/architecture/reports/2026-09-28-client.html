RS Planner

RS Planner is a small internal tool for scheduling projects, tracking the team's availability and matching people to work by skill. The architecture is in good shape overall — there are no rule-breaking dependencies between areas of the app — but two testing gaps and one code-organisation issue are worth a decision.

All findings

From context/architecture/findings.md, with evidence.

mediumAR-001

No automated tests protect the planner's scheduling and roster features

The tool that checks how much of the app is covered by automated tests isn't set up yet, so we can't measure test coverage for the scheduling calendar or the team roster — the two areas that change most often.

Add an automated test-coverage check, then write tests for the workload/utilization calculations and the scheduling logic first, since those change the most and matter the most.

lowAR-002

No automatic check for unused code

There's no tool installed that flags files or dependencies nobody uses anymore. Nothing unused was found this time, but leftover code could go unnoticed until one is added.

Add a dead-code checker (a one-time setup task) so unused files and dependencies get flagged automatically going forward.

lowAR-003

Shared helper code is tangled up with scheduling logic

A shared code file mixes generic, app-wide helpers with logic that really belongs to the scheduling calendar. This makes it look like the whole app changes every time someone tweaks scheduling, which makes it harder to see where the real risk and activity is.

Split that file into a generic part and a scheduling-specific part, so future reports show accurately which feature is actually changing.
