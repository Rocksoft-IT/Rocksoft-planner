# Research: Styling/colour architecture and theming surface for issue #68

**Date**: 2026-09-15 **Researcher**: rs-research (Claude Sonnet 5) **Git Commit**: d60fe4ffe8e6ff04bd12ae01b945f4dda5529267 **Branch**: autofix/cezar-issue-68-3a6137f0 **Repository**: Rocksoft-IT/Rocksoft-planner

## Research Question

Issue #68 asks for a per-user light/dark theme stored on the Supabase profile, switched from an avatar menu, applied to every authenticated screen without a flash, while sign-in/registration/password-reset stay dark always. Since this touches colour declarations across essentially every screen, the question is broad by necessity: how does Tailwind/colour styling work today (config, tokens vs hardcoded classes, CSS variables), what is the Supabase schema/migration/RLS convention for the new preference column, how is the current SSR/auth flow structured (to design a no-flash mechanism), and exactly which files/components own which coloured surfaces (Timeline sub-parts, People, Projects, Kompetencje, shared UI primitives, auth pages)?

## Summary

RS Planner has **no theming infrastructure at all** today: no `tailwind.config.*` (Tailwind 4 CSS-first, `@import "tailwindcss"` only), no `dark:` variant anywhere, no `darkMode` config, no CSS custom properties for colour, no design-token layer. All colour is either a hardcoded Tailwind utility class (slate/indigo dominate, ~260 and ~90 occurrences respectively across 25/21 files) or a raw hex string applied via inline `style` (project/avatar colours, availability-bar status colours, scrollbar colours). `class-variance-authority` and all six installed `@radix-ui/*` packages are dependencies with **zero usages** in `src/` — dead weight today, but `@radix-ui/react-dropdown-menu` is a ready-made, already-installed primitive for the new avatar menu.

The `profiles` table has no `theme` column; RLS already allows a user to update their own row (`profiles: update own`), so a client-side `.update()` is unblocked by policy. The `(dashboard)` layout is a Server Component that already fetches the full `profiles` row before rendering `<Sidebar>` — a `theme` column would arrive there "for free" (it already does `select('*')`), making a flash-free, SSR-rendered initial theme class straightforward without any new query. The `/auth/*` pages have no shared layout with `(dashboard)` and never receive `profile` — they are already structurally isolated from anything the dashboard layout does, so leaving them untouched satisfies "always dark" by construction.

`Modal.tsx` (the one truly shared UI primitives) is reused by all 5 modals across all 4 areas (People, Projects, Kompetencje, Timeline). Timeline-only filters (`PeopleFilter`, `ProjectFilter`, `SkillsFilter`, `MonthPicker`) are confirmed consumed only by `Timeline.tsx` — People/Projects/Kompetencje have no shared filter components with Timeline and only a thin overlap with each other (`RoleSelect`'s `ROLES` constant, `TagMultiSelect` inside Kompetencje only). This makes the four screen areas (Timeline / People+Projects / Kompetencje) file-disjoint from each other once the shared `Modal.tsx` and the theme mechanism itself are pulled into one foundational slice.

The highest-risk spots are **JS-computed colours**, which a blanket `dark:`/class sweep cannot touch: `formatAvailability()` (`src/lib/utils.ts:143-196`) returns bare hex literals including the over-allocation `#ef4444` red that must "stay clearly red in both themes," and the allocation-block renderer (`Timeline.tsx:169-189`) uses the *same* raw `project.color` hex as both a background tint source and the literal text colour — a combination that reads fine on today's dark backdrop but is not guaranteed to stay legible once the page backdrop turns light.

## Detailed Findings

### Tailwind 4 setup and existing colour vocabulary

- No `tailwind.config.*` anywhere in the repo — Tailwind 4 CSS-first config. `src/app/globals.css:1-29` is the entire stylesheet: `@import "tailwindcss"` (`:1`), one custom property `--font-sans` aliasing the Next `Inter` font (`:4`), a `* { box-sizing: border-box }` reset, and hardcoded hex custom-scrollbar rules (`:16-29`, `#1e293b`/`#334155`/`#475569`).
- `postcss.config.mjs:1-5` — only `@tailwindcss/postcss`. `package.json`: `"tailwindcss": "^4"`, `"@tailwindcss/postcss": "^4"`, plus `"clsx": "^2.1.1"`, `"tailwind-merge": "^3.6.0"`, `"class-variance-authority": "^0.7.1"` (dependencies) and six `@radix-ui/react-*` packages (`avatar`, `dialog`, `dropdown-menu`, `popover`, `select`, `tooltip`) — **all unused in `src/`** (confirmed by grep for `@radix-ui` and `cva(`), i.e. already paid for in the dependency tree but not wired into any component.
- Zero `dark:` variant usages anywhere under `src/` (`.tsx`/`.ts`/`.css`), no `darkMode` key anywhere in the repo, no `.dark` selector in any CSS file. `node_modules` is not installed in this worktree, so exact Tailwind 4 dark-mode/custom-variant syntax could not be verified against the installed package docs here — per `AGENTS.md`, this must be checked against the installed docs at implementation time before writing CSS.
- Colour-class density (grep, `.ts`/`.tsx` under `src/`): slate (`bg-/text-/border-slate-`) ≈ 262 occurrences across 25 files; indigo ≈ 89 across 21 files; `ring-` ≈ 32 across 13 files; red ≈ 17 across 11 files; emerald/amber ≈ 5 each. No `blue-` usage. Hottest files: `src/components/timeline/AllocationModal.tsx` (42 slate + 9 indigo), `src/components/timeline/Timeline.tsx` (24 slate + 4 indigo), `src/components/ui/PeopleFilter.tsx`, `src/app/(dashboard)/people/PeopleClient.tsx`, `src/components/ui/ProjectFilter.tsx`, `src/app/(dashboard)/competencies/CompetenciesClient.tsx`, `src/app/auth/register/page.tsx`, `src/components/competencies/CompetencyEditor.tsx`, `src/components/projects/ProjectModal.tsx`, `src/components/timeline/TimeOffModal.tsx`.
- No design-token abstraction exists. `src/lib/utils.ts` holds the closest thing: `cn()` (`:13-15`, `clsx`+`tailwind-merge`), `PROJECT_COLORS` (`:99-112`, 12 fixed hex swatches), `AVATAR_COLORS` (`:114-123`, 8 fixed hex swatches, subset of the above), `hexToRgba()` (`:198-203`, pure alpha-blend, **no luminance/contrast logic anywhere in the codebase**), and `formatAvailability()` (`:143-196`) which itself returns a third, informal hardcoded status-colour palette (`:173-179`). `src/lib/types.ts:70-74` (`TIME_OFF_LABELS`) embeds a fourth hardcoded hex palette keyed by time-off type.

### Supabase schema, RLS, and migration convention

- `profiles` columns today (`supabase-schema.sql:10-20`): `id, email, full_name, role, capacity_hours_per_day, is_admin, avatar_color, created_at, updated_at`. No `theme` column.
- RLS (`supabase-schema.sql:109-123`): `"profiles: authenticated read all"` (any signed-in user can read any profile), `"profiles: update own"` (`using (auth.uid() = id)`, no `with check` — sufficient for a client `.update()` scoped to the caller's own row), `"profiles: admin update all"`. No policy change needed for a new `theme` column.
- `handle_new_user()` trigger (`supabase-schema.sql:23-42`) seeds `full_name`/`role`/`avatar_color` from `raw_user_meta_data` on signup but does **not** seed every column (e.g. `capacity_hours_per_day` is not seeded either) — relying on the column's own `DEFAULT` for unseeded columns is the established pattern.
- Migration files (`migrations/`, sorted): `2026-07-16-allocation-updated-by.sql`, `2026-07-20-allocation-actor-trigger.sql`, `2026-07-28-competency-base.sql`, `2026-08-19-consolidate-allocation-actor-trigger.sql`, `2026-09-01-delete-team-member.sql`. Filename convention: `YYYY-MM-DD-kebab-case-description.sql`.
- `migrations/2026-07-16-allocation-updated-by.sql` (read in full) shows the exact WHY/HOW convention: a banner header with `Migration:`/`Feature:` (WHY), a second `HOW TO RUN` banner plus a deployment-ordering `IMPORTANT` note, then `alter table ... add column if not exists ...` (idempotent, single-column add needs no `DO $$` block), a one-time backfill `update`, and a superseded step kept **commented out with an explanatory note** rather than deleted ("so this file stays an accurate record of what was originally run") — migrations are never edited after the fact. Elsewhere, the CHECK-constraint idempotency pattern is `alter table ... drop constraint if exists ... ; alter table ... add constraint ... check (...)` (`supabase-schema.sql:266-268`), and a simple inline enum-style check is `check (kind in ('skill','technology'))` (`supabase-schema.sql:175`).
- The "migration + mirrored edit in `supabase-schema.sql`" convention is confirmed both by evidence (the `updated_by` column from the 2026-07-16 migration is present verbatim in `supabase-schema.sql:69`) and by explicit comments in `supabase-schema.sql` pointing back at the migration file for WHY/HOW rationale (`:167-170`, `:462-465`).

### Auth flow, SSR structure, and where a theme class can be applied without a flash

- `src/app/layout.tsx` (root, Server Component, no `'use client'`): `<html lang="en" className="... h-full antialiased">` (`:14`, no colour class), `<body className="min-h-full flex flex-col bg-slate-950">` (`:15`). Renders every route, including `/auth/*`.
- `src/app/(dashboard)/layout.tsx` (Server Component): calls `supabase.auth.getUser()` (`:8`), redirects to `/auth/login` if absent (`:10`), fetches `profiles.select('*').eq('id', user.id).single()` (`:12-16`), and renders `<div className="flex h-screen bg-slate-900 overflow-hidden"><Sidebar profile={...}/><main className="flex-1 overflow-auto">{children}</main></div>` (`:19-24`). A `theme` column will land in this `select('*')` with **no new query**.
- `src/app/auth/` has **no `layout.tsx`** — only `callback/route.ts`, `forgot-password/page.tsx`, `login/page.tsx`, `register/page.tsx`, `reset-password/page.tsx`, each a standalone client component rendering directly under the root layout with its own hardcoded `bg-slate-950` (e.g. `login/page.tsx:34`). They never receive `profile` and are not children of `(dashboard)/layout.tsx` — structurally isolated already, so "always dark" requires zero change to these files or to the root layout.
- `src/components/ui/Modal.tsx` (read in full, 42 lines) renders its overlay/panel as a plain `fixed inset-0` div **directly in the component tree — no `ReactDOM.createPortal`, no portal anywhere in the codebase**. This matters: a CSS class scoped to an ancestor element (rather than `<html>`) will still reach every modal, since modals stay DOM-descendants of whatever wraps the page content even though they are visually `position: fixed` overlays.
- Client Supabase usage: `src/lib/supabase/client.ts` wraps `createBrowserClient`. No existing client component currently does `.from('profiles').update(...)` (none found), but the same `.update(...).eq('id', ...)` pattern already exists for sibling tables via the browser client in `src/components/projects/ProjectModal.tsx:58`, `src/components/people/PersonModal.tsx:58`, `src/components/timeline/TimeOffModal.tsx:62`, `AllocationModal.tsx:127`, `Timeline.tsx:365,398,413,439` — a theme-persist call would mirror this exact convention.
- `src/app/api/*` route handlers (`competencies`, `employees`, `employees/[id]/competencies`, `search/experts`) are all read-only (GET, plus one search POST) and none touch `profiles` — confirmed no overlap risk with the read-only Competency API the issue says must not change.

## Architecture Insights

- **No theming layer exists; this is a from-scratch build**, not a refactor of an existing dark/light abstraction. The safest way to guarantee "the dark theme looks the same as it does today, screen for screen" (FR-006, the change's hardest acceptance criterion, explicitly flagged as the real risk by the issue) is additive: leave every existing hardcoded class exactly as it is (it already *is* the dark appearance) and layer new light-mode-only overrides on top, scoped to a `.light` ancestor class, rather than rewriting the base classes to represent a different (e.g. token-based) default. A rewrite-based approach would touch and risk every one of the same ~350 colour-class occurrences anyway, with no corresponding safety benefit given there is no automated visual regression coverage to catch a mistake.
- **The dashboard wrapper div, not `<html>`, is the natural place to scope the theme.** Since `(dashboard)/layout.tsx` already fetches the full profile row before rendering, and `Modal.tsx` renders in-tree (no portal), scoping a theme class to the dashboard wrapper div (`(dashboard)/layout.tsx:19`) rather than to `<html>` in the root layout: (a) requires no new query, (b) requires no change to the root layout or to any `/auth/*` page, (c) still reaches every modal despite their `fixed` positioning, because CSS descendant selectors don't care about `position`.
- **File-disjointness falls out naturally by area.** Once the one shared cross-area primitive (`Modal.tsx`) and the theme mechanism itself are handled in one place, Timeline (`Timeline.tsx`, `AllocationModal.tsx`, `TimeOffModal.tsx`, `MonthPicker.tsx`, `PeopleFilter.tsx`, `ProjectFilter.tsx`, `SkillsFilter.tsx`, `TimelineClient.tsx`), People+Projects (`PeopleClient.tsx`, `PersonModal.tsx`, `RoleSelect.tsx`, `ProjectsClient.tsx`, `ProjectModal.tsx`, `ColorPicker.tsx`), and Kompetencje (`CompetenciesClient.tsx`, `CompetencyEditor.tsx`, `ExperienceModal.tsx`, `TagMultiSelect.tsx`) touch entirely disjoint file sets and can be built independently in parallel.
- **JS-computed colours are the real risk surface**, not the Tailwind-class sweep. `formatAvailability()`'s bare hex literals and the allocation-block's "text colour = the same hex as the background tint's source" pattern are the two spots that cannot be fixed by adding `light:`-prefixed classes — they need theme-aware logic or an explicit decision to leave them and rely on the Tailwind 500-weight palette's inherent both-theme legibility (true for the status colours) versus needing an actual fix (true for the allocation-block text-on-tint pattern, since the tint's backdrop luminance flips with page theme while the palette is a fixed 12-swatch set including light colours).
- **`@radix-ui/react-dropdown-menu` is already installed and unused** — the natural, lowest-new-dependency-risk choice for the new avatar menu, in contrast to hand-rolling a fourth ad-hoc `useState`+outside-click dropdown pattern.
